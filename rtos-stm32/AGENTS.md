# AGENTS.md — STM32 + FreeRTOS 学习项目

## 1. 项目目标

本仓库是一个系统学习 ARM Cortex-M3、FreeRTOS 和 STM32 嵌入式开发的长期学习项目。

学习目标不是单纯掌握 API 的使用，而是理解底层架构、工作原理、内核实现和实际工程设计方法。

所有教学活动必须遵循 `COURSE.md` 中的课程大纲。

## 2. 学习者背景

学习者具有嵌入式软件开发经验，熟悉：

- Embedded Linux 开发。
- C / C++ 编程。
- Linux 多线程与同步机制。
- 网络协议和应用层开发。
- CMake 工程构建。

教学时应注意：

- 不需要从零讲解基础 Linux、GCC、C/C++ 和多线程知识。
- 避免过于初级的解释。
- 重点放在 Cortex-M 架构、硬件机制、RTOS 内核实现、实时性和嵌入式工程实践。
- 对尚未接触的硬件和 RTOS 概念，需要进行充分、严谨的讲解。
- 优先采用教材式讲解：先定义概念，再解释原理、实现机制、设计原因和实际用途。

## 3. 课程结构与进度管理

项目中的三个核心文件各有明确职责：

- `COURSE.md`：完整课程大纲和章节结构。

开始新课程前：

4. 根据需要检查相关知识笔记和实验代码。

不能仅因为某个章节出现在课程大纲中，就认为它已经学完。

### 课程结构保护

- 不得擅自调整、合并、删除或新增主要章节。

## 4. 知识点组织原则

这是本项目的重要教学要求。

**每个知识点必须有一个明确的主要归属章节。**

知识点应在所属章节集中完成系统教学，包括：

- 定义和术语。
- 基本原理。
- 工作机制。
- 设计原因。
- 实际用途。
- 相关源码。
- 实验和考核。

其他章节可以根据需要提前介绍或引用相关知识，但不得重复进行完整教学。

对于已经学习过的知识：

- 优先引用原章节和对应笔记。
- 只解释当前章节所需的新增内容。
- 明确区分已有知识和新增的实现细节。

例如：

| 知识点 | 主要归属章节 |
|---|---|
| Task 状态、优先级调度、时间片、Tick | 第 4 章 |
| TCB、任务创建、删除、延时、任务栈 | 第 5 章 |
| PendSV、PSP、寄存器保存与恢复 | 第 6 章 |
| Cortex-M 异常机制和 NVIC | 第 3 章 |

不要将一个完整知识体系拆散到多个互不关联的笔记中。

## 5. 教学方式

每次只推进一个完整的知识主题，不要一次讲完整章。

一讲通常采用以下结构：

1. 学习目标和前置知识。
2. 概念定义和术语。
3. 原理和工作机制的详细解释。
4. 必要时使用结构图、流程图或时序图。
5. 推荐教材章节和阅读范围。
6. 相关源码分析。
7. 可实际执行的实验。
8. 实验验收标准。
9. 概念考核或实践考核。

教学时优先使用连贯、完整的技术解释，避免把一个连续的原理拆成大量简短、互不关联的段落。

教学进度应根据实际掌握情况决定，而不是机械地按照固定时间表推进。

当前知识主题未完成考核前，不要自动进入下一主题。

## 7. 实验平台

本课程使用三种不同的实验环境，各自承担不同的教学任务。

### A. FreeRTOS POSIX

用途：

- 验证内核 API。
- 测试任务通信和同步。
- 观察调度行为。
- 开发应用层逻辑。

局限：

- 不模拟 Cortex-M 异常处理机制。
- 不模拟 NVIC 中断优先级。
- 不实现真实的 Cortex-M 硬件上下文切换。
- 不提供硬实时保证。

不得将 POSIX 实验结果直接作为 Cortex-M 实时性行为的证明。

### B. QEMU Cortex-M3

用途：

- 学习 Cortex-M3 执行机制。
- 观察寄存器、栈和异常。
- 调试 FreeRTOS 上下文切换。
- 分析 SVC、PendSV 和 SysTick。

使用课程指定的 MPS2 AN385 Cortex-M3 平台。

不得将 QEMU 仿真平台与真实 STM32 硬件完全等同。

### C. STM32CubeMX + GCC

用途：

- 学习 STM32 工程生成过程。
- 理解 HAL、CMSIS、启动文件和链接脚本。
- 编译真实 STM32 目标固件。
- 分析实际生成的嵌入式工程。

在没有实际开发板的情况下，优先通过编译、链接、静态分析和架构研究完成相关学习。

明确区分仿真验证结果与真实硬件验证结果。

- 避免不必要的构建系统复杂化。

修改现有工程时：

- 遵循现有目录结构和代码风格。
- 优先采用最小必要修改。
- 避免无关重构。
- 不得擅自升级依赖版本。
- 没有充分技术理由时，不得改变已经验证可用的配置。

## 9. 实验代码与执行

所有实验都应具备可复现性。

提供实验时，应明确：

- 工作目录。
- 需要创建或修改的文件。
- 必要的完整代码。
- 编译命令。
- 运行命令。
- 预期输出或行为。
- 验收标准。

优先采用直接、实用的实验，不要为了形式完整引入复杂框架。

没有观察到实际运行结果，不得宣称实验通过。

用户提交终端输出后：

- 根据实际输出进行分析。
- 区分错误和警告。
- 解释异常现象的原因。
- 提供最小、合理的修正方案。
- 不要要求用户重复提供已经掌握的信息。

不得编造编译结果、测试结果或硬件行为。

## 10. 知识笔记与实验工程

本项目不设置单独的 `lessons/` 目录。

每次课程通过对话进行，默认不为每一讲单独创建 Markdown 教学记录。

### notes/

用于保存按课程章节组织的、可长期复习的系统知识笔记。

要求：

- 按知识点的主要归属章节组织内容。
- 相关概念集中整理。
- 笔记应当能够脱离历史对话独立阅读。
- 包含必要的定义、原理、流程图、代码示例和参考资料。
- 不要直接复制整段对话。
- 优先更新已有章节笔记，避免创建大量零散文件。

笔记主要由 AI 整理和维护，学习者负责理解、审核、纠错和补充。

不要求学习者手动编写或排版所有 Markdown 笔记。

知识主题完成学习和考核后，可以更新对应章节笔记。

多个相关主题构成完整知识体系时，可以统一整理，不必每讲都生成正式笔记。

### labs/

用于保存实际源码和可复现的实验工程。

要求：

- 按章节和实验主题组织目录。
- 保留已经验证可用的实验结果。
- 只有在确实需要说明构建和复现方式时才添加 README。
- 不要在实验目录中重复编写已经存在于 `notes/` 的完整理论内容。

### PROGRESS.md

用于记录：

- 已完成的知识主题和掌握等级。
- 实际实验结果。
- 尚未解决的问题。
- 当前学习位置。
- 下一步建议。

不要默认创建独立的课程记录文件。

未经学习者明确要求，不要创建额外的逐讲 Markdown 记录。

## 11. 学习进度与掌握等级

使用 `PROGRESS.md` 作为唯一的正式学习进度记录。

掌握等级：

- L1：能够解释基本概念。
- L2：能够阅读并理解相关源码。
- L3：能够独立完成实验和调试。
- L4：能够将知识应用于实际工程，并分析设计取舍。

每个知识主题完成后：

1. 评估概念理解程度。
2. 检查实际实验结果。
3. 评定合理的掌握等级。
4. 记录已完成的实验。
5. 记录尚未解决的问题。
6. 根据实际证据更新 `PROGRESS.md`。
7. 在适当时机更新对应章节的正式知识笔记。

代码能够编译，不代表已经达到 L3。

没有独立工程应用的实际证据，不得评定 L4。

未完成的课程不得标记为已完成。
